## Viability verdict

**Viable with changes.** The architecture (operations table, queued jobs, no-op terminate, live-expiry guard) is sound and most of it is implemented as planned. Three things drive the "with changes":

1. **The #1416 refund guard does not actually cover the #1416 case** (finding C1). The plan's own premise — refund re-renews the service — moves `expires_at` forward another term, which creates a _new_ idempotency key and a target one term beyond the registrar, so the code renews (and pays) again. This needs a different guard (invoice-linked, or bounded by the last paid term).
2. **A failed registration leaves an ACTIVE service**, not a pending one (finding H1); Paymenter core sets the service active before `createServer` runs. AC5/TS5 cannot be met as written without the extension resetting the status or the plan being amended.
3. **Doc validation found three concrete code-vs-docs mismatches** — contact IDs must be -1 for several TLDs on register (H7), `ping()` uses `no-of-records=1` where the minimum is 10 (H2), and the documented non-whitelisted-IP message matches none of the code's heuristics (M6) — plus a handful of response-shape assumptions the readable articles simply don't show (`recsindb` paging, numeric row keys in actions results, `actionstatus` values, `endtime` format, the cost-price keys). None of those invalidates the design — each is isolated in one class — but phase 0 on the demo account stays mandatory, exactly as the plan says.

Resolved in the plan's favour during this review: the live base URL is `https://httpapi.com/` (code's default is right); the legacy HTTP API remains the documented API (the v2 developer portal is "coming soon"; only the SOAP kits are deprecated); `invoice-option` and `auto-renew` are required on register/renew and the code already sends them; `domsecret` is retrievable via details.json (phase-2 auth-code feature is feasible); yearly billing units and rule-object checkout validation are confirmed in Paymenter source.

## Live results (2026-11-11, test.httpapi.com, dev account)

Run with `RC_WRITE=1 RC_ID=… RC_KEY=… vendor/bin/phpunit --testsuite Live`: 9 pass, 1 incomplete (renew and nameserver change on an active domain need demo funds). Offline suites: 45 passing.

Bugs found only by real calls, now fixed:
- **Signup password:** `customers/signup.json` requires an alphanumeric password of 8 to 15 characters; the code sent 24 hex characters, so every new customer would have failed.
- **Lowercase error status:** `register.json` answers `{"status":"error","error":"…"}` with HTTP 200. The client matched only `ERROR`, so a failed registration looked like a submitted one with no order ID.
- **Unknown action ID:** `actions/search-current.json` answers HTTP 500 `{"status":"ERROR","message":"No record found"}`; it threw and would have stopped the five-minute poller. It now reads as "unknown".
- **Cost-price keys:** `.com` is `domcno` (also `domorg`, `dombiz`, `dominfo`, `domus`, `thirdleveldotuk`); only 328 of 389 domain keys follow `dot<tld>`. Without an alias list `.com` pricing would never have synced.

Confirmed against the real API: `addnewdomain` price maps (string values), search rows keyed `"1"`… with `recsonpage`/`recsindb`, action rows keyed the same with `eaqid`/`actionstatus`/`actionstatusdesc`, `orderid.json` returns an ordinary API error for an unknown domain, `customers/details.json` returns "Customer … not found" as an API error, signup and add-contact return bare integers, `register.json` response has `entityid`/`eaqid`/`actionstatus`, `details.json` has `ns1`/`ns2`, and the demo registry accepts `ns1.domain.com` (not `ns*.google.com`).

New facts that change the plan:
- **Insufficient funds is silent at register time.** `register.json` returns an order ID and action ID; the order stays `InActive` with action status `InvoicePaid` / "Order Locked In Processing", and the reason ("Reseller has insufficient funds") appears only in `details.json`. The plan's "operation fails clearly" funds scenario (TS6) therefore needs a different signal; the poller now at least shows the registrar's status text when it gives up.
- **Inactive orders refuse writes cleanly:** renew → "Order is Inactive", modify-ns → "Invalid Order status".
- **`endtime` is absent until the order is active**, so its format is still unconfirmed; an inactive order correctly produces no renewal and no expiry-sync row.
- Pending action status seen: `InvoicePaid`. Success and failure strings are still unseen.

## Findings

### Critical

**C1 — The renewal guard does not cover the issue-#1416 refund case it was designed for.**

- Severity: critical. Where: plan §Core flows / §Renewal listener; code [RenewalService.php:51](extensions/Servers/ResellerClub/Core/RenewalService.php#L51), [RenewOnServiceUpdated.php:39](extensions/Servers/ResellerClub/Listeners/RenewOnServiceUpdated.php#L39). Breaks AC2 / TS3.
- Mechanism: Paymenter's re-renewal (the plan's own description of #1416) runs `RenewServiceService::handle`, which sets `expires_at = calculateNextDueDate()` — for an active service that is **current `expires_at` + another term** ([RenewServiceService.php:26](paymenter-src/app/Services/Service/RenewServiceService.php#L26), [Service.php:127-140](paymenter-src/app/Models/Service.php#L127-L140)). The listener sees a forward change, creates a _new_ key `renew:{id}:{new_expires_at}`, and the job's guard compares the live registrar expiry to a target now one term **ahead** of it — so it calls `renew.json` again. The reseller pays for a term the customer was refunded.
- The plan's claim "the registrar expiry is already at the target, so no second call is made" is only true when the duplicate event carries (nearly) the same `expires_at`. The test that covers this ([LifecycleTest.php:81-93](extensions/Servers/ResellerClub/tests/Feature/LifecycleTest.php#L81-L93)) models the re-renewal as `target + 1 day`, which is inside the 3-day tolerance — it encodes the wrong premise.
- Fix: tie renewals to paid invoices rather than to `expires_at` deltas (listen for the renewal invoice's payment, or store the last-paid-term boundary and refuse to create a renew operation whose target exceeds it), or at minimum refuse/flag a second renew operation for the same service within one billing period and alert the admin instead of calling the registrar.

### High

**H1 — A failed registration leaves the service ACTIVE, not pending.**

- Severity: high. Where: [ResellerClub.php:129-137](extensions/Servers/ResellerClub/ResellerClub.php#L129-L137) (comment on 133 claims "service stays pending" — it does not); root cause in core: [RenewServiceService.php:19-28](paymenter-src/app/Services/Service/RenewServiceService.php#L19-L28) dispatches `CreateJob` and _then_ sets the service active and saves; the zero-price cart path does the same ([Cart.php:236-242](paymenter-src/app/Livewire/Cart.php#L236-L242)). Breaks AC5 / TS5. [PHASE0.md:24](extensions/Servers/ResellerClub/PHASE0.md#L24) documents this as "known core behaviour to accept", contradicting the plan.
- Failure scenario: domain taken between checkout and payment → `createServer` throws → CreateJob fails (tries=1) → customer sees an **active** domain service with no actions; only the admin operations list shows the truth.
- Fix: in the `createServer` failure path, set the service back to pending (or a custom note) before throwing, and/or render a "registration pending/failed" state on the service page when `rc_order_id` is absent. Update the plan either way.

**H2 — `ping()` uses `no-of-records=1`, below the documented minimum of 10.**

- Severity: high. Where: [LegacyHttpClient.php:34](extensions/Servers/ResellerClub/Registrar/LegacyHttpClient.php#L34). Doc: cnlogin.resellerclub.com/kb/answer/771 — `no-of-records` is required and "must be 10 to 500" (summary-sourced). Breaks AC6.
- Failure scenario: with valid credentials, `domains/search.json?no-of-records=1` is likely rejected with `status: ERROR` → `testConfig` reports an API error instead of `true`, making the connection test useless and indistinguishable from a real fault.
- Fix: use 10. (One-character change; verify on the demo account.)

**H3 — Nameserver changes are a synchronous registrar write in the web request, and a timeout is treated as failed, not unknown.**

- Severity: high. Where: [Nameservers.php:51-54](extensions/Servers/ResellerClub/Livewire/Nameservers.php#L51-L54) → [NameserverService.php:36-41](extensions/Servers/ResellerClub/Core/NameserverService.php#L36-L41). Breaks plan §Queue ("All registrar writes run as queued jobs… a worker restart or duplicate dispatch cannot send a second write") and §Failure modes ("Timeout on a write: treat as unknown").
- Details: the write runs inside the Livewire request (up to 30s cURL timeout blocking the page); the idempotency key includes `bin2hex(random_bytes(4))` ([NameserverService.php:32](extensions/Servers/ResellerClub/Core/NameserverService.php#L32)), so every click is a fresh operation — the rate limiter (5 per 5 min) is the only duplicate-write protection; and the `catch (RegistrarException)` marks a TIMEOUT as failed with no lookup-before-retry.
- Fix: record the operation and dispatch a `ShouldBeUnique` job (like register/renew) keyed `nameservers:{service_id}:{hash}`; honour `isOutcomeUnknown()`.

**H4 — Expiry sync pagination depends on an undocumented `recsindb` key; without it, only the first 100 domains are ever synced.**

- Severity: high (silent). Where: [LegacyHttpClient.php:188-205](extensions/Servers/ResellerClub/Registrar/LegacyHttpClient.php#L188-L205) (`recsindb`, numeric row keys, both marked UNCONFIRMED in code), [ExpirySync.php:72](extensions/Servers/ResellerClub/Core/ExpirySync.php#L72). Doc: answer/771 lists response fields but no example JSON and no `recsindb`/`recsonpage`.
- Failure scenario: if the real response lacks `recsindb`, `total` falls back to the page's row count, `$seen < $res->total` is false after page 1, and domains 101+ never get `rc_expiry` updates or silent-renewal-failure detection (plan §Reconciliation).
- Fix: verify the shape in phase 0; safer loop: continue while a page returns ≥1 order row, with a hard page cap.

**H5 — Action polling assumes rows keyed `"1"` and guesses the `actionstatus` vocabulary; if either is wrong, every successful operation is eventually marked failed.**

- Severity: high (unverified, not a confirmed bug). Where: [LegacyHttpClient.php:173-186](extensions/Servers/ResellerClub/Registrar/LegacyHttpClient.php#L173-L186) (`$res['1'] ?? $res[1]`), [Dto.php:64-72](extensions/Servers/ResellerClub/Registrar/Dto.php#L64-L72) (`isCompleted`: success/completed/complete; `isFailed`: failed/failure/error/rejected). Doc: answer/908 confirms the fields (`actionstatus`, `actionstatusdesc`, `eaqid`) but shows no row-key example and does **not** enumerate status values (the plan said the same).
- Failure scenario: unknown key shape → `ActionStatus('unknown')` every poll → after 24 polls (~2h) [ActionPoller.php:25-29](extensions/Servers/ResellerClub/Core/ActionPoller.php#L25-L29) marks the operation failed ("Action did not complete in time") even though the registration/renewal succeeded — admins see false failures and may retry paid operations.
- Fix: record real responses in phase 0 (the plan's contract-test layer); make the parser scan all array-of-array entries and match on `eaqid`; treat unknown statuses as still-pending with escalation, which the code already does — the risk is the key shape and the enum.

**H6 — `endtime` format under the renewal guard is unverified (endpoint and field names now doc-confirmed).**

- Severity: high → narrowed. Where: [LegacyHttpClient.php:140-152](extensions/Servers/ResellerClub/Registrar/LegacyHttpClient.php#L140-L152). answer/770 confirms `domains/details.json`, `options=All`, `endtime` ("Registry expiry date") and `ns1`/`ns2` — the endpoint is no longer guesswork. What the article does **not** state is whether `endtime` is epoch seconds or a date string. The renewal guard, the renew `exp-date` argument and the expiry sync all `(int)`-cast it; a date string would cast to 0/garbage.
- Failure scenario: `endtime` non-numeric → `expiresAt = 0` → guard never satisfied → renew called with `exp-date=0`, rejected (best case) or mis-processed.
- Fix: phase-0 recording, **plus** a code guard: refuse to renew when `orderDetails()` returns `expiresAt <= 0`.

**H7 — Register sends the same contact ID for all four roles; several TLDs require -1 for admin/tech/billing contacts.**

- Severity: high. Where: [LegacyHttpClient.php:108-111](extensions/Servers/ResellerClub/Registrar/LegacyHttpClient.php#L108-L111) — `reg-/admin-/tech-/billing-contact-id` all set to `$r->contactId`. Doc: answer/752 — admin-contact-id must be **-1** for .EU/.RU/.UK; tech-contact-id -1 for .EU/.FR/.RU/.UK; billing-contact-id -1 for .BERLIN/.CA/.EU/.FR/.NL/.NZ/.RU/.UK/.LONDON. The plan's endpoint table also missed this.
- Failure scenario: every registration of a .uk, .eu, .ca, .nl, .nz, .fr (etc.) domain fails or is rejected by the registry because a real contact ID is passed where -1 is mandated.
- Fix: a per-TLD contact-role map in the client (or product attributes), defaulting the affected roles to -1. Add .uk/.eu to the phase-0 demo matrix.

### Medium

**M1 — Renewal term derived from the timestamp delta, not the plan.**

- Where: [RenewOnServiceUpdated.php:37](extensions/Servers/ResellerClub/Listeners/RenewOnServiceUpdated.php#L37): `round((new-old)/365d)`, min 1. A monthly plan (the plan's own fallback if yearly units were unsupported) or an admin catch-up produces a 1-year registrar renewal for a 1-month payment; a >10-year delta would exceed registry maximums. Yearly plans (which `TldProducts` creates) behave correctly. Fix: read `plan->billing_unit/billing_period` and skip or alert for non-year units.

**M2 — Any manual forward edit of `expires_at` in the admin triggers a paid registrar renewal.**

- Where: same listener; no linkage to invoices. The plan chose `expires_at` as the renewal signal, so this is design-consistent, but a goodwill extension by an admin silently spends reseller funds. Fix folds into the C1 fix (invoice-linked renewals); until then, document it.

**M3 — Cart items added before the registrations switch is turned off are not "rejected at checkout with a clear message".**

- Where: plan §Registration switch vs [Cart.php:173-243](paymenter-src/app/Livewire/Cart.php#L173-L243) — `Cart::checkout` creates services/invoices without re-running the checkout-config validation rules; `RegistrationsOpen` only runs when the product config page is submitted. The `createServer` backstop ([RegistrationService.php:35-37](extensions/Servers/ResellerClub/Core/RegistrationService.php#L35-L37)) still prevents a silent registration, so the safety property holds; the promised UX does not.

**M4 — Expiry sync can stamp a still-in-flight renewal as failed.**

- Where: [ExpirySyncRunner.php:31-32](extensions/Servers/ResellerClub/Core/ExpirySyncRunner.php#L31-L32) selects the newest renew op in `submitted` **or** completed; [ExpirySync.php:60-65](extensions/Servers/ResellerClub/Core/ExpirySync.php#L60-L65) marks it failed when the registrar expiry lags. A renewal submitted shortly before the daily sync, whose action has not completed, gets marked failed; the five-minute poller may then flip it back to completed. Fix: only blame `completed` operations, or skip ops younger than an hour.

**M5 — `ensureCustomer` treats every lookup error as "customer does not exist".**

- Where: [LegacyHttpClient.php:58](extensions/Servers/ResellerClub/Registrar/LegacyHttpClient.php#L58) (`$throwOnError=false` swallows all `status: ERROR` responses). A transient or auth-ish error on `customers/details.json` leads to a `signup` attempt, which fails with "username already exists" — a misleading registration failure for returning customers without the `rc_customer_id` property. Fix: swallow only a "not found"-classified error; rethrow the rest.

**M6 — IP-whitelist detection heuristics do not match the documented error message.**

- Where: [LegacyHttpClient.php:238-240](extensions/Servers/ResellerClub/Registrar/LegacyHttpClient.php#L238-L240) (HTTP 403, or body containing "ip" **and** "not allowed") and [classify():257-268](extensions/Servers/ResellerClub/Registrar/LegacyHttpClient.php#L257-L268) ("whitelist" / "ip address"). Doc: answer/753 says a non-whitelisted IP gets **"Access Denied. You are not allowed to perform this action."** — that string contains neither "ip", "whitelist" nor "ip address", so unless the response is also HTTP 403, the error is classified as a generic API error and `testConfig` loses its IP-specific message (AC6). The transport status code for this case is still unverified.
- Fix: match on "not allowed to perform" / "access denied" for the IP case (and record the real HTTP status in phase 0). The auth/funds/taken wordings in `classify()` remain unverified phase-0 items.

**M7 — `invoice-option=NoInvoice` now doc-validated as required on register and renew; exact billing effect still a demo check.**

- Where: [LegacyHttpClient.php:112,161](extensions/Servers/ResellerClub/Registrar/LegacyHttpClient.php#L112). answer/752 and /746 both list invoice-option as **required** (NoInvoice / PayInvoice / KeepInvoice / OnlyAdd) — the code was right to send it and the plan's register row should add it. "NoInvoice: raises no invoice and executes" matches the plan's assumption; confirm on the demo account that the reseller debit account is charged. Downgraded from an open risk to a demo confirmation.

**M9 — `purchase-privacy` is always sent, but the parameter is unsupported for many TLDs.**

- Where: [LegacyHttpClient.php:113](extensions/Servers/ResellerClub/Registrar/LegacyHttpClient.php#L113) sends `purchase-privacy=true|false` on every registration. Doc: answer/752 — purchase-privacy is not supported for .US, .UK, .EU, .DE, .CA, .FR, .NL, .NZ, .RU, .ASIA (renew has a similar list). A product with "Buy privacy protection by default" on an unsupported TLD will fail or mis-handle at registration; even sending `false` may be rejected on those TLDs (unverified).
- Fix: omit the parameter unless privacy is requested, and gate it per TLD (product attribute), matching the plan's "hide the control where the registrar refuses".

**M8 — `CostTable::parse` guesses the cost-price response shape.**

- Where: [CostTable.php:14-33](extensions/Servers/ResellerClub/Core/CostTable.php#L14-L33), marked UNCONFIRMED. If the real keys differ, pricing sync silently proposes nothing (empty table) — benign failure mode, but the nightly job and `TldProducts` pricing both produce nothing until fixed. Phase 0.

### Low

**L1 — `/domains` route can be shadowed by a category slug** (noted in PHASE0.md): [routes/web.php:7](extensions/Servers/ResellerClub/routes/web.php#L7) vs Paymenter's catch-all category routes. Verify on a real install.

**L2 — Multiple ResellerClub servers: search and admin actions use only the first** ([Search.php:36](extensions/Servers/ResellerClub/Livewire/Search.php#L36), [ListOperations.php:39](extensions/Servers/ResellerClub/Admin/Resources/OperationResource/Pages/ListOperations.php#L39)). Fine for one server; silent divergence with two.

**L4 — `.UK` availability nuance missed by plan and code:** answer/764 says .UK allows only one name per availability call (for `ror` handling). With one label per call the code is fine; just a doc note.
